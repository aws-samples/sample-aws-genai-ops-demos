## 1. Requirements

### 1.1 Summary

Phase 1 proves the architecture move with the cheap path only: a scoped operator opens
the dashboard, scopes to their area of duty (tag / account / region), clicks **Rescan my
scope**, and a server-side durable execution discovers deprecated-runtime Lambda
functions (Trusted Advisor + Lambda API + CloudWatch) and assesses each (Nova complexity
+ target runtime), populating a DynamoDB inventory keyed `account#region#arn`. The
browser holds no AWS credentials; it calls an HTTP API with a Cognito JWT. The Migrate
wizard shell exists but its final submit is disabled ("coming soon").

### 1.2 Functional requirements

- **FR1 — Durable Discover+Assess as one execution.** A single Lambda durable function
  (durable execution enabled at creation, invoked via a `live` alias / qualified ARN)
  runs Discover then Assess as durable steps, with `context.map` fan-out over functions
  and per-item failure tolerance. Ports the logic in `agent/discover/main.py` and
  `agent/analyze/main.py`. (plan §3.4, §9.1)
- **FR2 — Discover step.** Trusted Advisor deprecated-runtime check (`L4dfs2Q4C5`) +
  Lambda `GetFunctionConfiguration`/`ListTags` + CloudWatch logs/metrics enrichment +
  Nova priority scoring with reasoning. (ports `agent/discover/main.py`)
- **FR3 — Assess step.** Download function code, Nova complexity / target-runtime
  assessment with constrained decoding, **in-process `ast.parse` + import check** of the
  transformed/analyzed Python (code parsed as data, never executed), replacing the
  AgentCore Code Interpreter. (ports `agent/analyze/main.py`; plan §5.4)
- **FR4 — Scoping.** Tag filter + multi-region + multi-account (hub-and-spoke, opt-in
  behind a flag, read-only spoke role) with single-account default. Bounded per-(account,
  region) units; one unreachable account fails only its own units. (plan §8.2)
- **FR5 — API.** HTTP API Gateway + Cognito JWT authorizer in front of a plain API
  Lambda exposing `POST /refresh`, `GET /refresh/{arn}`, `POST /actions`. Browser holds
  no AWS credentials. (models `aws-services-lifecycle-tracker` api-stack.ts + api.py)
- **FR6 — Data model.** Inventory keyed `account#region#arn`; rows carry `account_id`,
  `account_name`, `region`. (plan §8.2)
- **FR7 — Stacks.** Keep Data and Auth; replace Runtime (3 CfnRuntime) with a new
  **Pipeline** stack; add an **Api** stack; keep Frontend repointed to the API URL.
  Tracking moves to Pipeline (main stack) in `cdk/bin/app.ts`, exact existing tag.
  (plan §5.1)
- **FR8 — Frontend.** Scoped inventory table home with Refresh showing durable steps;
  delete `agentcore.ts`, add `api.ts`; cut Dashboard/charts/4-source grid/MigrationPlan/
  Transform tab; add the Migrate wizard shell with final submit disabled. (ui-proposal §1–7)
- **FR9 — Deploy scripts.** `deploy-all.ps1/.sh` call only `shared/scripts/
  check-prerequisites.*` then `shared/scripts/deploy-cdk.*`; never call cdk directly.
  README stack table updated. (contributor-guide)

### 1.3 Non-functional requirements

- **NFR1 — No hardcoded regions / model ids.** Region via `shared/utils/aws-utils.ts` in
  CDK and env vars in Lambdas; Bedrock model id computed in CDK and passed as a Lambda env
  var. (contributor-guide; current code hardcodes `global.amazon.nova-2-lite-v1:0` — see
  §7 Risk R3)
- **NFR2 — Replay safety.** All non-determinism (Bedrock, boto3, uuid, time) inside steps.
  (skill critical rules)
- **NFR3 — $0 standing cost, ~5-min deploy** preserved (no containers, no VPC). (plan §5.5)
- **NFR4 — Demo-quality, secure defaults.** Least-privilege IAM, no secrets in step
  results, Cognito JWT auth, code parsed never executed.

### 1.4 Acceptance criteria (numbered, testable)

1. `cdk list` shows exactly `LambdaRuntimeMigrationData-<region>`, `...Auth-<region>`,
   `...Pipeline-<region>`, `...Api-<region>`, `...Frontend-<region>` and **no**
   `...Runtime-<region>` — these five regardless of the `-MultiAccount` flag, which in
   Phase 1 adds only hub-side IAM + context (no sixth stack; see §5).
2. No `aws-cdk-lib/aws-bedrockagentcore` import remains in `cdk/`; no `CfnRuntime` exists.
3. The pipeline Lambda is created with `durableConfig` and exposes a `live` alias; its
   role has `AWSLambdaBasicDurableExecutionRolePolicy`. (matches lifecycle `pipeline-stack.ts`)
4. The solution-adoption tag `(uksb-do9bhieqqh)(tag:lambda-runtime-migration,operations-automation)`
   appears on the Pipeline stack only, set in `cdk/bin/app.ts`, and nowhere else.
5. `POST /refresh` starts (or adopts) a durable execution and returns an execution ARN;
   `GET /refresh/{arn+}` (greedy — durable ARNs contain `/`) returns status + per-phase
   progress; both require a valid Cognito JWT (401 without).
6. After a refresh, the DynamoDB inventory contains rows keyed `account#region#arn` with
   `account_id`/`region` populated; the UI table shows them scoped and sorted by urgency.
7. A single function whose Discover or Assess step fails does not fail the whole run; the
   run summary reports it. (`context.map` tolerated-failure)
8. `frontend/src/agentcore.ts` is deleted; `frontend/src/api.ts` exists and is the only
   path to the backend; the browser obtains no AWS credentials.
9. The Migrate wizard renders three steps (Assess / Decide / Review and start migration);
   the final submit button is disabled with a "coming soon" affordance.
10. `deploy-all.ps1` and `deploy-all.sh` deploy all five stacks via
    `shared/scripts/deploy-cdk.*` only, end with a user-friendly summary printing the
    dashboard URL and region, and never invoke `cdk` directly.
11. `cdk.json` `app` is `npx ts-node --prefer-ts-exts bin/app.ts` (unchanged).

### 1.5 Out of scope (Phase 2+)

AWS Transform / `atx` / CodeBuild; the conditional `VcsTarget` (CodeCommit) stack;
opening a merge request; the full multi-account rollout StackSet (Org/Spoke stacks beyond
what Phase 1 scoping needs); scheduled autonomous sweep; rehearsal diff artifacts;
GitHub/Bitbucket adapters. (plan §5.5 Phase 2/3)

### 2.1 Pipeline stack (`cdk/lib/pipeline-stack.ts`) — NEW

Direct analog of `aws-services-lifecycle-tracker/cdk/lib/pipeline-stack.ts`. Decisions:

- **Language: the backend is Python** (ports the existing Python agents; lifecycle
  tracker's backend is Python too). CDK stays TypeScript. The stack bundles a Python
  Lambda from a `backend/` directory using `lambda.Code.fromAsset` with the same
  **local-bundle-then-Docker-fallback** pattern (`bundleBackendLocally` / `tryBundle`) the
  lifecycle `pipeline-stack.ts` uses, so Windows deploys without Docker. Runtime:
  `lambda.Runtime.PYTHON_3_13`, `Architecture.ARM_64`. (lifecycle pipeline-stack.ts;
  current agents target `PYTHON_3_13`)
- **Shared util staging.** The current CDK app imports `shared/utils/aws-utils.ts` in
  `bin/app.ts` (TypeScript) for region. The Python Lambda needs the region/model-id
  helpers at runtime; follow the lifecycle pattern of copying `shared/utils/aws_utils.py`
  into the staged backend at synth (`stageBackend()`), so there is no `sys.path` hack and
  one source of truth. (lifecycle pipeline-stack.ts `SHARED_AWS_UTILS`)
- **Two Lambdas, one bundle:** `pipeline` (durable; handler `pipeline.handler`) and `api`
  (plain; handler `api.handler`), both from the same `backendCode` asset. (lifecycle)
- **Durable config + alias (verified against lifecycle `pipeline-stack.ts` — `durableConfig`
  prop, `live` alias off `currentVersion`, and the managed policy all match the sibling
  verbatim; no re-derivation needed):**
  ```ts
  this.pipelineFunction = new lambda.Function(this, 'PipelineFunction', {
    /* ... */ durableConfig: {
      executionTimeout: cdk.Duration.minutes(30),  // ceiling; a Phase-1 Discover+Assess run is minutes
      retentionPeriod: cdk.Duration.days(14),
    },
  });
  this.pipelineFunction.role!.addManagedPolicy(
    iam.ManagedPolicy.fromAwsManagedPolicyName('service-role/AWSLambdaBasicDurableExecutionRolePolicy'));
  this.pipelineAlias = new lambda.Alias(this, 'PipelineLiveAlias', {
    aliasName: 'live', version: this.pipelineFunction.currentVersion });
  ```
  `durableConfig` is a verified `lambda.Function` prop in this repo's `aws-cdk-lib`
  version (lifecycle tracker uses it); no extra construct library is needed for the CDK
  surface. The durable SDK is a **Python dependency** in `backend/requirements.txt`
  (`aws_durable_execution_sdk_python`), not a CDK construct. (plan §6; skill
  deployment-iac)
- **IAM (pipeline role, least-privilege):** a fixed role name
  (`lambda-migration-pipeline-role-<region>`) so spoke trust can pin it; statements ported
  from `runtime-stack.ts` minus S3-write-for-transform and minus all AgentCore/Code
  Interpreter actions:
  - `support:DescribeTrustedAdvisorCheckResult` (TA; us-east-1 client — partition-home, see §3)
  - `lambda:GetFunction`, `GetFunctionConfiguration`, `ListTags`, `ListVersionsByFunction`
  - `logs:DescribeLogStreams`, `logs:DescribeLogGroups`; `cloudwatch:GetMetricStatistics`
  - `dynamodb:GetItem/PutItem/UpdateItem/Query/Scan` on the inventory table + indexes
  - `s3:GetObject/PutObject/ListBucket` on the migration bucket (Assess writes
    `analysis.json`, same as today)
  - `bedrock:InvokeModel`, `bedrock:Converse` scoped to `foundation-model/*` and
    `inference-profile/*` (not `*`), matching lifecycle's `BedrockModelInvocation`
  - `AWSLambdaBasicDurableExecutionRolePolicy` managed policy
  - **Multi-account (opt-in):** `sts:AssumeRole` on `arn:<partition>:iam::*:role/<SPOKE_ROLE_NAME>`
    and `organizations:List*/Describe*` reads — only wired when the scoping needs it (§5).
- **API Lambda role** adds durable-control actions on the pipeline function ARN:
  `lambda:InvokeFunction`, `lambda:GetDurableExecution`, `lambda:GetDurableExecutionHistory`,
  `lambda:ListDurableExecutionsByFunction` (verified names from lifecycle pipeline-stack.ts),
  plus `ec2:DescribeRegions` for a Settings region list. Env var `PIPELINE_FUNCTION_ARN`
  = the `live` alias ARN.
- **Model id env var (decided — no CDK-side option).** `get_bedrock_model_id` exists
  **only in Python** (`shared/utils/aws_utils.py`); `shared/utils/aws-utils.ts` has no
  `getBedrockModelId`, so computing the id in the TypeScript CDK stack is **not** an
  available path and is not used. Instead, **compute `MODEL_ID` at Lambda init** from the
  staged Python `aws_utils.py` (already staged by `stageBackend()` for the region helper)
  and pass the computed env var into the Lambda's own `MODEL_ID` for the agents to read.
  Concrete rules the implementer must follow (fixes R3; the review's H2/M1):
  - **Pass the UNPREFIXED base id** `amazon.nova-2-lite-v1:0` to `get_bedrock_model_id`.
    The helper *prepends* the CRIS prefix (`us.`/`eu.`/`apac.`/`global.`) based on region;
    feeding it the current hardcoded `global.amazon.nova-2-lite-v1:0` would double-prefix to
    `us.global.amazon.nova-2-lite-v1:0` (or `global.global.…`), invalid at invoke time.
  - **Always pass the explicit Nova base name.** The helper's default `model_name` is a
    Claude id (`anthropic.claude-sonnet-4-6`); call it as
    `get_bedrock_model_id("amazon.nova-2-lite-v1:0")`, never with the default.
  - The resulting region-prefixed id is never hardcoded. Use the same computed `MODEL_ID`
    for both the pipeline Lambda and the API Lambda (both read it from env).
- **No SNS/SQS/Scheduler in Phase 1** (lifecycle has them for its weekly schedule; the
  Lambda demo's scheduled sweep is Phase 3). Keep the stack minimal.

## 3. Durable function — step / map structure and replay boundaries

File: `backend/pipeline.py`, handler `pipeline.handler`, decorated `@durable_execution`.
Structure mirrors `aws-services-lifecycle-tracker/backend/pipeline.py`.

### 3.1 Input contract
```json
{
  "scope": { "tags": [{"key": "BU", "values": ["payments"]}], "regions": ["us-east-1"],
             "accounts": [{"id": "...", "name": "..."}] },
  "refresh_origin": "manual"
}
```
`normalize_spec(event)` (pure, outside steps) **validates then defaults**. It raises a
typed `SpecValidationError(ValueError)` carrying the offending field name on any violation;
the API Lambda maps that to `400 {error: "<field>: <reason>"}` (§6). Validation runs
*before* any step/checkpoint so ambiguous input can never cross a replay boundary. Rules:

- `scope` absent/empty `{}` → defaulted (not rejected): hub account only, this function's
  own region, no tag filter.
- `scope.tags`, if present, must be a list of objects; each `tags[].key` a **required
  non-empty string**; each `tags[].values` a **list of strings** (empty list = "key exists"
  match). Any other shape → error naming `scope.tags[i]`.
- `scope.accounts`, if present, must be a list of objects; each `accounts[].id` must match
  **`^\d{12}$`**; `accounts[].name` optional string. Empty/absent → hub account only
  (single-account default, §5).
- `scope.regions`, if present, must be a **list of strings**, each a syntactically valid
  region token (`^[a-z]{2}-[a-z]+-\d$`), **capped at `MAX_REGIONS` (5)** — over-cap is
  **rejected** with an error (not silently truncated), so the operator knows their scope was
  not fully honored. Empty/absent → this function's own region.
- `refresh_origin`, if present, must be one of `manual` | `scheduled` (Phase 1 only
  produces `manual`); unknown → error.

All checks are field-named; `normalize_spec` returns a fully-defaulted, validated spec that
the steps consume without re-checking.

### 3.2 Steps and map (replay-safe)

The whole run is **Discover then Assess**, both as `context.map` fan-outs over functions,
tolerating per-item failure. Pure folding happens outside steps on step return values.

```
handler(event, context):
  spec = normalize_spec(event)                     # pure
  run  = context.step(start_run(spec), name="start-run")      # mint run_id, time, region, resolve accounts/regions

  # DISCOVER
  cells = discover_cells_for(spec, run.regions, run.accounts) # pure: (account, region) units
  disc  = context.map(cells, _discover_scope, name="discover",
                      config=MapConfig(max_concurrency=5, completion_config=TOLERATE_ALL))
  # each _discover_scope -> context.step(discover_scope(cell, run_id)):
  #   TA query (L4dfs2Q4C5) for that (account,region) + per-function Lambda/CloudWatch
  #   enrichment + Nova priority scoring; writes rows account#region#arn; returns bounded facts

  # ASSESS
  arns = context.step(list_discovered_arns(run_id, scopes), name="list-discovered")  # read keys back (bounded)
  asmt = context.map(arns, _assess_one, name="assess",
                     config=MapConfig(max_concurrency=5, completion_config=TOLERATE_ALL))
  # each _assess_one -> context.step(assess_one(arn)):
  #   download code, Nova complexity/target assessment, in-process ast.parse+import check,
  #   update row (complexity, target_runtime, deprecated_apis, breaking_changes, caveats)

  return context.step(summarize(run, spec, disc_summary, asmt_summary), name="summarize")
```

Replay-boundary rules enforced (skill critical rules; current code violates several
because it runs in AgentCore, not durable):
- **`start_run`** is the only place `uuid.uuid4()` and `datetime.now()` are called; today
  these are scattered across `agent/discover/main.py` (`now = datetime.now(...)`,
  `time.sleep`). They move inside `start_run` / their step.
- **Every boto3 and Bedrock call lives inside a step** (`discover_scope`, `assess_one`).
  No client is created at module import for use outside a step.
- **`time.sleep(3)` TA retries** in `agent/discover/main.py` are **removed**; durable
  step retry replaces them via `StepConfig(retry_strategy=...)` (lifecycle `_EXTRACT_RETRY`
  pattern). A step that reads TA and finds nothing simply returns empty; the step-level
  retry/`context.wait` handles flakiness deterministically.
- **Step results are bounded** (counts, keys, labels) — the full function list is written
  to DynamoDB inside the step and only keys cross checkpoints, mirroring lifecycle issue
  #225 (`scan_cell` writes rows, returns facts). Prevents large/non-deterministic payloads
  crossing a checkpoint.
- **No secrets/PII returned from steps**: env var values are already masked to `***` in
  the current `enrich_function`; keep that.
- **`context.map` tolerated failure**: `CompletionConfig(tolerated_failure_percentage=100)`
  so one bad function/account never aborts the run (AC7; plan §8.2 "one unreachable account
  fails only its own units").

### 3.3 Diff logic
The current `handle_discover` diff (new / existing / resolved / re-opened against the
inventory) is preserved, but refactored so each **scope's** diff is computed inside its
`discover_scope` step from rows read for that scope (keeping the per-(account,region) unit
boundary). The cross-scope "resolved" sweep that today retries TA is replaced by: a row
not re-seen in its own scope's successful discover is marked resolved **only if that scope
succeeded** (never delete/resolve data for a scope that failed — plan §8.2).

### 3.4 In-process validation (replaces Code Interpreter)
Inside `assess_one`, after Nova returns the assessment, run `ast.parse(source)` on each
Python source file and a best-effort import-name check (collect `import`/`importFrom`
names via the AST, never execute). Node/.NET: skip parse (no in-process parser). Code is
**data**, never run. (plan §5.4)

`syntax_ok` is **tri-state**: `true` (parsed clean), `false` (SyntaxError on a Python
source), or **`null` = "not applicable"** for non-Python runtimes (Node/.NET) where no
in-process parser ran. The step records `null`, not `true` and not a missing attribute, so
the UI can distinguish "validated and passed" from "nothing to validate" — per
contributor-guide "say what was not checked" and demo-lab-ui-guide "every word has a
label". `unresolved_imports` is an empty list for the `null` case. Assess renders the three
cases distinctly (see §7.1).

### 3.5 Partition-home clients (global services)
TA/Support is partition-global, not us-east-1. The current code hardcodes
`region_name="us-east-1"` for Support (`agent/discover/main.py`). Replace with the
partition-home mapping from contributor-guide:
`SUPPORT_HOME = {"aws":"us-east-1","aws-cn":"cn-north-1","aws-us-gov":"us-gov-west-1"}`
and derive from `boto3.session.Session().get_partition_for_region(region)`. (contributor-guide
"Global services follow the partition")

## 4. Data model (keyed account#region#arn)

Current `DataStack` table `lambda-runtime-migration` has `partitionKey: function_arn` and
a GSI `migration-status-index` (pk `migration_status`, sk `priority_score`). This
**collides across accounts** (same ARN format, and `function_arn` alone cannot carry an
account prefix cleanly). Change (plan §8.2 keying rule, mirrors lifecycle
`<kind>#<account>#<region>#<id>`):

- **New partition key `item_key`** = `fn#<account_id>#<region>#<function_arn>`. Keeps
  `function_arn`, `account_id`, `account_name`, `region` as attributes.
- Keep the GSI on `migration_status` (pk) + `priority_score` (sk) for status queries.
- This is a **breaking schema change** → the table is recreated (RemovalPolicy.DESTROY is
  already set; demo-quality, no migration). Document in README that a redeploy resets the
  inventory. (data-stack.ts)

Row attributes (superset of today's, with scope keys added):
`item_key, function_arn, account_id, account_name, region, runtime, alert_status,
deprecation_date, days_to_deprecation, avg_daily_invokes, invocation_count_14d,
package_type, memory_size, timeout, handler, tags{}, layers[], migration_status,
first_seen_at, resolved_at, priority_score, priority_label, priority_reasoning,
migration_complexity, target_runtime, assessment_summary, migration_risks, deprecated_apis[],
breaking_changes[], dependency_issues[], lines_of_code, num_source_files,
syntax_ok (tri-state: true | false | null="not applicable" for non-Python runtimes),
unresolved_imports[], s3_findings_path, assessed_at`.

`migration_status` values Phase 1: `DISCOVERED`, `ASSESSED`, `SKIPPED` (container image),
`RESOLVED`. Phase-2 values (`MIGRATING`, `PR_OPEN`, `MERGED`, `FAILED`) are reserved but

## 5. Scoping model

Single-account is the default; a single-account user must never see multi-account. (plan §8.2)

- **Tag filter**: carried in the `scope.tags` of the `/refresh` body and honored by
  `discover_scope` (filters the TA/Lambda results by the function's tags). Also applied
  client-side for the inventory view (lifecycle `scopeInventory`).
- **Multi-region**: `scope.regions` → one discover cell per region (default: the function's
  own region). Bounded (reuse lifecycle's `MAX_REGIONS = 5` cap concept).
- **Multi-account (opt-in)**: behind a `-MultiAccount` / `--multi-account` deploy flag and
  a read-only preflight (`shared/scripts/check-org-access.*`), exactly as lifecycle does.
  The pipeline role assumes a fixed-name read-only **spoke role** per member account; the
  discover cell runs its boto3 session with the assumed-role credentials. **Phase 1 does
  NOT build the Org/StackSet rollout** — only the hub-side assume-role + the scoping data
  model. Deploying the spoke role across accounts stays a documented manual step / Phase 2.
  (plan §8.2 "Do NOT build the full multi-account rollout StackSet beyond what Phase 1
  scoping needs"; task scope item 3)
- **Unit of work** = one `(account, region)` discover cell + one `assess_one` per function.
  One unreachable account fails only its own cells (tolerated-failure map); the summary
  reports `accounts_failed`.

## 6. API contract

API Lambda `backend/api.py`, modeled on lifecycle `api.py`. Two invocation shapes: HTTP
API (payload v2, JWT already enforced) and direct invoke (tests). JSON bodies; `_http()`
helper for responses.

| Method / path | Body | Returns | Notes |
|---|---|---|---|
| `POST /refresh` | `{scope?, refresh_origin?}` | `202 {executionArn, executionName, alreadyRunning:false}` or `200 {executionArn, alreadyRunning:true}` | Starts or **adopts** the running execution. Invokes the pipeline **`live` alias** with `DurableExecutionName` (manual → `refresh-manual-<ts>`); adopt via `list_durable_executions_by_function(... Statuses=["RUNNING"])`. (lifecycle `start_refresh`) |
| `GET /refresh/{arn+}` | — | `200 {executionArn, status, startDate, stopDate, summary?, progress{phases[]}, error?}` | `get_durable_execution` + `get_durable_execution_history` folded into phases for the Steps UI. (lifecycle `refresh_status` / `_progress_from_history`) |
| `POST /actions` | `{action, ...}` | `200 {...}` | Router. Phase-1 actions: `list_functions` (scoped inventory read), `list_regions` (`ec2:DescribeRegions`), `get_metrics` (summary strip counts). Migrate actions are **not** wired. |

Progress phases exposed by `/refresh/{arn}` for `RefreshSteps`: **Prepare the run**
(`start-run`), **Discover deprecated functions** (`discover-*`, gen-AI sparkle — Nova
priority), **Assess each function** (`assess-*`, gen-AI sparkle — Nova assessment),
**Summarize** (`summarize`). Phase derivation copies lifecycle `_progress_from_history`
(StepStarted/StepSucceeded/StepFailed counting, prefix match, `stopped` when run ended).

The pipeline-arn stripping (`_unqualified_function_arn`) and the typed step-result decoder
(`_decode_step_result`) are ported verbatim from lifecycle `api.py`.

## 8. Error handling (per operation)

| Operation | Failure | Recoverable? | Caller sees | Logged |
|---|---|---|---|---|
| `POST /refresh` with no `PIPELINE_FUNCTION_ARN` | config error | fatal (bug) | `500 {error}` | API Lambda error log |
| `/refresh` while one is RUNNING | not an error | n/a | `200 {alreadyRunning:true}` | info |
| TA `SubscriptionRequiredException` (no Business/Enterprise Support) | expected | recoverable | discover step returns 0 functions + a `message`; run succeeds, summary notes "TA unavailable: Support plan" | warning (per contributor-guide "say what was not checked") |
| TA generic `ClientError` | transient | recoverable | step retried (`StepConfig`), then empty + message | error |
| `discover_scope` for one (account,region) throws (e.g. AssumeRole denied) | per-unit | recoverable | that cell counts failed; `accounts_failed` in summary; other scopes unaffected | error |
| `assess_one` download fails / Image package type | per-function | recoverable | row marked `SKIPPED` (Image) or assess step failed (tolerated); UI shows caveat | warning |
| Nova `converse` returns no `toolUse` | per-function | recoverable | assess step fails for that function (tolerated); fallback priority used in discover (current fallback kept) | error |
| `ast.parse` SyntaxError | data finding, not a failure | n/a | `syntax_ok:false` stored + shown in Assess | info |
| DynamoDB write fails in a scope | per-unit | recoverable | step raises → scope fails → its previous inventory left intact (never partial reconcile) | error |
| `GET /refresh/{arn}` history read fails | best-effort | recoverable | `progress` falls back to counters, never raises (lifecycle `_progress_from_history` try/except) | swallowed |
| API call without valid JWT | auth | fatal for that request | `401` from the authorizer | API GW |

Input validation (`/refresh`): the body must be JSON (else `400`); the scope object is then
validated by `normalize_spec` per the enumerated rules in §3.1 (`tags[].key` non-empty
string, `tags[].values` list of strings; `accounts[].id` matches `^\d{12}$`; `regions` a
list of valid region strings capped at `MAX_REGIONS=5`, over-cap **rejected**; valid
`refresh_origin`). Each violation raises the typed `SpecValidationError`, which the handler
maps to `400 {error: "<field>: <reason>"}` with the offending field named — validation
happens before the pipeline is invoked, so no bad spec reaches a durable step. Unknown
`/actions` action → `{error}`; unknown route → `404`. (lifecycle `api.py` handler)

## 11. Open decisions & risks

- **R1 — Backend language.** Chosen **Python** (ports existing agents, matches lifecycle).
  Alternative TypeScript backend was rejected: it would mean rewriting both agents from
  scratch and diverging from the sibling pattern this task says to model on.
- **R2 — Table recreation.** The `item_key` schema change recreates the table (data loss).
  Accepted for a demo (RemovalPolicy.DESTROY already set); documented. If preserving data
  mattered we would add a migration, out of scope.
- **R3 — Hardcoded model id (resolved in §2.1).** Current agents hardcode
  `global.amazon.nova-2-lite-v1:0`. §2.1 now states the concrete rule: compute `MODEL_ID`
  at Lambda init via the staged Python `get_bedrock_model_id("amazon.nova-2-lite-v1:0")`
  — passing the **unprefixed** base (the helper prepends the CRIS prefix; feeding the
  already-`global.`-prefixed string would double-prefix) and the **explicit Nova base**
  (the helper defaults to a Claude id). There is no TypeScript `getBedrockModelId`, so CDK
  computation is not used. The only residual open item is whether **Nova-2 Lite is available
  via the resolved CRIS profile in every deployment region** — the implementer should
  confirm per target region or fall back to an equivalent available Nova id; never
  re-hardcode a region-prefixed id.
- **R4 — `durableConfig` / SDK versions.** **Verified against lifecycle
  `pipeline-stack.ts`** (same repo, same `aws-cdk-lib`): `durableConfig` is a real
  `lambda.Function` prop, the `live` alias is built off `currentVersion`, and
  `AWSLambdaBasicDurableExecutionRolePolicy` is attached — no re-derivation needed. The one
  open item is the exact `aws_durable_execution_sdk_python` version to pin in
  `backend/requirements.txt`; copy the version lifecycle's `backend/requirements.txt` pins.
- **R5 — Durable control IAM action names. Verified against lifecycle `pipeline-stack.ts`:**
  `lambda:InvokeFunction`, `lambda:GetDurableExecution`, `lambda:GetDurableExecutionHistory`,
  `lambda:ListDurableExecutionsByFunction` all match the working sibling verbatim. No open
  item; the coder should not re-spend effort confirming these.
- **R6 — Multi-account depth.** Phase 1 builds only hub-side assume-role + scoping data
  model, not the Org/Spoke StackSet. If the demo must *show* multi-account end-to-end,
  deploying the spoke role is a manual step until Phase 2. Flagged so the review can decide
  whether that is enough for Phase 1.
- **R7 — Wizard route vs overlay.** Recommend a `/migrate?arns=...` route (exit-guard and
  browser-back behave naturally) over an in-place overlay (ui-proposal §3). Low risk; UI
  detail.
- **R8 — Trusted Advisor dependency.** Discover depends on TA check `L4dfs2Q4C5`, which
  needs Business/Enterprise Support. In accounts without it, Discover returns empty with a
  message (not a failure). The demo seeding story (a real deprecated-runtime Lambda to find)
  is **[UNVERIFIED]** for Phase 1 — the current demo relies on TA finding real functions;
  whether to seed one is an open product decision (lifecycle/plan seed a `python3.9` function
  but that is tied to the Phase-2 CodeCommit repo).
- **R9 — Auth stack change ordering.** Dropping the Identity Pool from `auth-stack.ts` is a
  destructive change to a deployed stack; on an existing deployment CDK will delete the pool
  and role. Acceptable (demo, no prod data), but the deploy script should deploy Auth before
  Api (Api's authorizer needs the user pool) — ordering captured in §9.
